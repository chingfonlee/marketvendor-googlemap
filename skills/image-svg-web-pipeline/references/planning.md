# 計畫文件（docs/PLAN.md）

PLAN 是整個專案的總合約。之後每份規格文件都要指回 PLAN 的某一節；PLAN 和其他文件衝突時，以日期新的決定為準，並回頭把舊的改掉。

## 範本

```markdown
# 開發計畫（第一版）

- 更新日期：YYYY-MM-DD
- 分工：<誰出圖、誰寫規格和程式、誰驗收>。每項完成後停下，等使用者驗收。

## 1. 目的與範圍
<網站做什麼用（展示？驗收？收集回報？），用一句話>
- 正式資料：<來源檔、數量，以哪份為準>
- 第一版只做：<頁面清單>
- 後端：<網頁確認後才開始 / 不做>

## 2. 畫面
| 位置 | 內容 |
|---|---|
<每一個區塊一列，對到設計圖>

互動規則：
- <點 A → B 怎麼變>
- <哪些操作不影響哪些區塊>

## 3. 狀態與數字的定義
| 狀態 | key | 定義 |
<完成率怎麼算、哪些排除、狀態怎麼轉換>

## 4. 資料匯入
- 輸入：<只讀，先複製到暫存再讀>
- 輸出：<公開 JSON 各有哪些欄位；匯入報告>
- **不輸出**：<個資欄位>
- 人工決定：記在 `data/review-decisions.csv`，重新匯入時套用，不改原始檔
- 固定 ID：第一次產生後存進 `data/id-map.json`，之後不變、不重用
- 可重跑：同一份輸入跑兩次，輸出完全相同

## 5. 表單 / 回報（如果有）
<流程、收什麼不收什麼、防重複、防濫用、紀錄欄位表>

## 6. 任務清單與驗收標準
| # | 任務 | 誰做 | 驗收標準 | 狀態 |
|---|---|---|---|---|

## 7. 未來擴充（不阻擋第一版）
<討論過但這版不做的東西，寫在這裡，之後不要再提>
```

## 寫任務清單的要點

- 一列一個可驗收的交付物，驗收標準寫成「可以檢查的句子」（例如「總數 347，三種狀態加總等於總數，跑兩次結果相同」），不要寫「做好響應式」。
- 狀態欄位在做完時改成連結到交付文件 + ✅，等驗收時寫「等驗收」。這讓 PLAN 本身就是進度表。
- 預設的順序可以參考 SKILL.md 的階段表；網頁全部確認之前不建立雲端資源。
- 任何範圍縮減（例如手機不放地圖、拿掉某分頁）都在 PLAN 改，並寫日期和原因。

## 資料問題

真實資料一定有問題（數量對不上、重複、歇業、名稱改了）。開一份 `docs/DATA_ISSUES.md`：

| # | 問題 | 影響 | 建議 | 決定 |

不要在匯入程式裡悄悄修正，所有修正都經過 `review-decisions.csv`，每筆附原因和日期，這樣可以追溯。

再加一支 `scripts/stats.py` 產生 `docs/STATS.md`，讓「最新數字」永遠由腳本算出來，不要手寫。
